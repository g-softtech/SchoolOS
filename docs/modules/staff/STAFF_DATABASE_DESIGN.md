# Staff Database Design

## Design Principles
- **Multi-tenancy**: Every core entity MUST include `tenantId`.
- **Soft Deletes**: Use `deletedAt` on `Employee` to preserve historical record for payroll, audit, and reporting. All child records (credentials, position history) cascade-delete only if the employee is hard-deleted, which is forbidden except by a Super Admin in extreme cases.
- **Immutable History**: `EmployeePositionHistory` and `IdentityCredential` records are NEVER deleted. They represent the factual audit trail.
- **Optimistic Locking**: Use a `version` field on `Employee` if concurrent HR workflows require it.

## Entity Relational Schema

### 1. Department
Supports a recursive parent-child hierarchy for nested organizational units.

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `tenantId` | UUID | FK → Tenant |
| `parentId` | UUID? | FK → Department (self-referential, nullable for root) |
| `name` | String | e.g. "Science", "Administration" |
| `description` | String? | |

*Index: `(tenantId)`*

### 2. Position
Defines a role within a department. Positions are reusable across employees.

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `tenantId` | UUID | FK → Tenant |
| `departmentId` | UUID | FK → Department |
| `title` | String | e.g. "Senior Teacher", "Principal" |
| `description` | String? | |
| `isTeachingRole` | Boolean | Baseline flag for Timetables |
| `roleCategory` | String | Enum: TEACHER, ADMINISTRATOR, VICE_PRINCIPAL, PRINCIPAL, FINANCE, LIBRARIAN, SECURITY, DRIVER, NURSE, WARDEN |

*Index: `(tenantId, departmentId)`*

### 3. Employee
The canonical employee record. Two statuses are tracked independently:

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `tenantId` | UUID | FK → Tenant |
| `userId` | UUID? | FK → Identity GlobalUser. Nullable. Never drives login directly. |
| `employeeNumber` | String | Tenant-scoped unique. Generated by configurable numbering strategy (e.g. `EMP-2026-0001`). |
| `firstName` | String | |
| `lastName` | String | |
| `email` | String? | HR contact email. NOT the login email (that lives in Identity). |
| `phone` | String? | |
| `dateOfHire` | DateTime | |
| `status` | String | **Employment status**: DRAFT, ACTIVE, ON_LEAVE, SUSPENDED, TERMINATED, ARCHIVED |
| `positionId` | UUID? | FK → Position (current position snapshot for fast reads) |
| `deletedAt` | DateTime? | Soft delete marker |

> ⚠️ **Important separation**: `Employee.status` is the **employment status**. The login account status lives entirely in the Identity module under `GlobalUser.isActive`. These MUST NOT be derived from each other. An HR administrator can suspend an employee while IT keeps their login account active for appeals, and vice versa.

*Unique: `(tenantId, employeeNumber)`. Index: `(tenantId, userId)`.*

### 4. EmployeePositionHistory
Immutable. One row per position change. Never deleted.

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `tenantId` | UUID | FK → Tenant |
| `employeeId` | UUID | FK → Employee |
| `positionId` | UUID | FK → Position |
| `departmentId` | UUID | FK → Department |
| `effectiveFrom` | DateTime | Start of this role |
| `effectiveTo` | DateTime? | End of this role (null = current) |
| `reason` | String | e.g. "Initial Hire", "Promotion", "Transfer", "Demotion" |

*Index: `(tenantId, employeeId)`.*

### 5. IdentityCredential
Abstract, technology-agnostic identity token. Immutable history — revocation sets `status`, never deletes.

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `tenantId` | UUID | FK → Tenant |
| `employeeId` | UUID | FK → Employee |
| `type` | String | QR, NFC, RFID, BARCODE, MANUAL, API |
| `token` | String | Cryptographically random (`crypto.randomBytes(32).toString('hex')`). Globally unique. |
| `status` | String | ISSUED, ACTIVE, SUSPENDED, REVOKED, EXPIRED |
| `issuedAt` | DateTime | |
| `expiresAt` | DateTime? | Nullable for non-expiring credentials |
| `lastRotatedAt` | DateTime? | Populated when credential is rotated |

> **Credential Rotation Rule**: Only ONE ACTIVE credential per `(employeeId, type)` at any time. Issuing a new credential of the same type must atomically revoke the existing one in the same database transaction. History is never pruned.

*Unique: `(token)`. Index: `(tenantId, employeeId, status)`. Index: `(token, status)` — this second index is the primary read path for Attendance scan lookups.*

---

## Key Indexes for Performance

The Attendance module will perform high-frequency `token` lookups during scan events. The compound index `(token, status)` on `IdentityCredential` must be present and benchmarked to ensure sub-50ms p99 latency.

## Future: StaffAssignment Table (Reserved)

The following table will be introduced when Timetables and Examinations require it. It is documented here to prevent premature fields from creeping into `Employee`.

| Field | Notes |
|---|---|
| `employeeId` | FK → Employee |
| `academicSessionId` | FK → AcademicSession |
| `role` | CLASS_TEACHER, SUBJECT_TEACHER, HOUSE_MASTER |
| `targetId` | FK → ClassSection or Subject |
| `effectiveFrom` | |
| `effectiveTo` | |

This keeps the `Employee` record clean as a permanent identity, while `StaffAssignment` tracks session-scoped teaching duties.
